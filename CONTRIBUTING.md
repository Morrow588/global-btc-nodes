# Contributing to AI Algorithmic Trading Starter

Thanks for taking the time to contribute. This document covers local setup, how we name branches and commits, how pull requests are reviewed, and the one rule that surprises people most: **the dataset in `data/` is generated by CI — don't hand-edit it.**

By participating you agree to follow our [Code of Conduct](CODE_OF_CONDUCT.md).

## Getting set up locally

Python 3.10 or newer is required (CI runs 3.11).

```bash
git clone https://github.com/virtualtradrs/ai-algo-trading-starter.git
cd ai-algo-trading-starter

python3 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

Check that your checkout is healthy before you change anything:

```bash
python scripts/check_repo.py
```

That script is the same one CI runs on every push. It checks that the community files, CI configuration and README structure are present, and it prints a readable list of what is missing and exits non-zero if anything is. If it passes locally, it will pass in CI.

## Finding something to work on

- Issues labelled [`good first issue`](https://github.com/virtualtradrs/ai-algo-trading-starter/labels/good%20first%20issue) are scoped to be completed in one sitting and name the files to touch.
- Issues labelled `help wanted` are open to anyone.
- Nothing fits? Open a <a href="https://github.com/virtualtradrs/ai-algo-trading-starter/issues/new/choose">feature request</a> describing the problem you want solved before writing a large patch — it is much cheaper to change direction on an issue than on a pull request.

Comment on the issue to say you are taking it, so two people don't duplicate work.

## Branch naming

`<type>/<short-description>`, lowercase with hyphens, using the same types as our commits:

| Prefix | Use for |
| --- | --- |
| `feat/` | new functionality, e.g. `feat/btc-node-rpc-fetch` |
| `fix/` | bug fixes, e.g. `fix/mempool-null-guard` |
| `docs/` | documentation only, e.g. `docs/quickstart-tweaks` |
| `chore/` | tooling, CI, dependencies, e.g. `chore/group-dependabot-prs` |
| `test/` | tests and fixtures only, e.g. `test/schema-roundtrip` |
| `refactor/` | behaviour-preserving restructuring |

Branch off `main` and keep the branch focused on one change. Rebase on `main` rather than merging it in, so the history stays linear.

## Commit messages — Conventional Commits

We use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```
<type>(<optional scope>): <description>

<optional body — why, not what>

<optional footer — e.g. Closes #42>
```

Examples:

```
feat(pipeline): fetch node telemetry over JSON-RPC
fix(schema): reject non-monotonic timestamps
docs: add quickstart for Windows users
chore(ci): pin actions to major versions
```

Rules of thumb:

- Imperative mood in the description ("add", not "added").
- The description completes the sentence *"Applying this commit will…"*.
- One logical change per commit. Don't fold unrelated formatting into a feature commit.
- Don't pad history. Commits whose only content is a whitespace tweak, a re-save or a graph-visible timestamp are not welcome here — this project's history is meant to be readable as a record of real work.

## Pull requests

1. Push your branch and open a PR against `main`. The PR template is not required; a clear description is.
2. Fill in **what changed**, **why**, and **how you verified it**. "How you verified it" means the exact command you ran and what it printed, not "tested locally".
3. CI must be green. The workflow runs the repository health check and a Python syntax check across `scripts/`.
4. A maintainer reviews for correctness first, then for style. Expect questions about edge cases, error handling and whether a claim in your docs is something you actually measured.
5. Keep the PR up to date with `main` (rebase, force-push your branch). Squash-merge is the default; the squash message must stay a valid Conventional Commit.

If a reviewer's suggestion doesn't make sense to you, say so in the thread. "Why?" is a perfectly good review comment.

## The dataset is generated by CI

`data/btc_node_metrics.json` and `data/btc_market_daily.csv` are written by the scheduled workflow and committed by a bot. That has three consequences:

- **Do not hand-edit files in `data/`.** Any manual change — adding a row, fixing a value, reformatting — is overwritten by the next scheduled run, and a PR that only edits `data/` will be closed.
- **Let CI finish before you rebase.** If the daily job commits while your branch is open, pull `main` (or rebase) and resolve the conflict in favour of the generated file, then re-run the pipeline notes if needed.
- **Report bad data as an issue, not a patch.** If a value looks wrong, include the timestamp, the field, the observed value, the expected value and the run URL that produced it. That lets us fix the *fetch or validation*, which is where the real bug is.

Schema changes to the dataset are a code change: update the fetch code, the validator and `data/README.md` in the same pull request, and explain how existing rows are migrated.

## Documentation claims

Please keep the README and docs verifiable:

- No invented benchmarks, accuracy figures, user counts or download numbers.
- Label anything not yet implemented as **planned** rather than describing it as working.
- If you quote a measurement, say how it was taken and from which dataset revision.

## Questions

Open an issue and tag it as a question — a maintainer will answer in the thread. Thanks again for helping make this useful.
